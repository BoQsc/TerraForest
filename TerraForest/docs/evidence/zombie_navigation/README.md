# Shared zombie navigation and wooden-door interaction — 2026-10-23

Zombies now execute the existing native `ActorRoute` local planner through
`NativeActorNavigator`. Their own controller retains animation, attack state and
one physical body. Standing movement uses the existing native grounded stair
motor. No duplicate native entity/store owns that body. The
[navigation standard](../../NAVIGATION_STANDARD.md) declares capabilities,
geometry, failure states, ownership, limits and interaction permissions.

The user's closed-door policy is **attack breakable doors when blocked**. The
current whitelist is the wooden-door model. An identified approach target exposes
the actual leaf shape to authored contact tests. Live placement, pose, protection,
reach, facing and solid occlusion are checked before damage. Existing native
durability and placement removal perform the world change, clear hinge/damage
state, invalidate routes and mark the world dirty. No player salvage or tool wear
is generated by NPC damage.

## Failures retained and resolved

`point_contact_failure/` records the initial door check's four failures: the
single contact point did not overlap authored hand markers. Exposing the actual
leaf box fixed contact; damage, destruction and subsequent player arrival pass.

`before_water_fix/` and `footprint_only_failure/` retain the water-route failures.
The zombie did not enter water, but the planner skipped a narrow shoreline corner
which its small movement guard rejected, causing repeated stalls. The shared core
now samples a conservative square footprint along the entire edge at <=0.1 m
intervals, including its start. The final debug and release detours reach the
player with no water crossing. Sampling is still discrete, not continuous hazard
geometry; tiny hazards between samples remain unqualified.

`character_world_failure/` retains two headless block-attack failures and their
diagnostic repeat. The correct block target, tool and edit availability were
present, but mouse mode was 0 (visible); gameplay `attack()` requires captured
mouse mode. The rendered debug and release checks report mode 2 and pass all 18
assertions. Use rendered execution for that input-dependent fixture. This does
not suppress or reclassify its failed headless results as passing runs.

The broader old combat/packaging baseline failures documented in
`../character_integration/README.md` remain open. Those full suites were not
rerun here; these passing scoped checks do not make the whole repository green.

## Remaining requirements

Local search is capped at +/-16 m and 2,048 nodes. Zombie and existing-actor pools
each have 12 planning work units and a cooperative 750 us deadline, so both pools
can consume 24 units, plus motion guards, bounded perception and admission
callbacks. Query/callback cost can overrun the deadline. Six residents and the
checks above do not establish population/frame-cost scalability.

Regional/portal routes and future-route streaming requests, floor/cave connections,
populated settlement journeys, moving-target endurance, heterogeneous avoidance,
automatic permitted ladder/jump links, tight crawler clearance and measured total
host CPU cost remain open. Crawlers use a conservative upright turning envelope
and are qualified only for level approaches, not stairs, slopes or low tunnels.
Door destruction still needs a fresh-process compound save/reopen check beyond
the provider snapshot round trip. See the standard and
[foundation register](../../WORLD_FOUNDATION_STATUS.md) for return triggers and
closing evidence. This is local navigation and one authorized interaction, not
complete whole-world navigation or survival gameplay.

Work remains isolated on `codex/character-integration`, based on world commit
`87390a2c`. Subsequent concurrent world changes require a source merge, joint
native rebuild and host regressions; their dirty checkout was left untouched.
