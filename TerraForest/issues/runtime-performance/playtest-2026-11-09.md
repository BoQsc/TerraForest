# First diagnostic playtest — 2026-11-09

Status: Problems reproduced; diagnosis only, no runtime correction. User visual
review remains open. Measured source revision: `b1070c57` (clean at launch).

The current build does not deliver consistently paced 60 FPS on this route.
Average FPS hides the problem. There is evidence for several separate costs,
but these tests do not establish that a wholesale architecture rewrite is needed.

## Method and scope

Two fresh processes used the existing graphical gameplay driver, with real
walking, sprinting, jumping and pickaxe/terrain transactions. Each did 24 changed
mining contacts and 22 physical jumps. Both functionally passed, preserved the
source save, made zero mouse captures and failed the existing performance gates.
This was scripted offscreen playtesting plus inspection of the arrival image,
not a human assessment of motion or a foreground input-to-display measurement.
Godot reported focus for all captured frames.

- Intel Core i5-12450H, RTX 4050 Laptop GPU, Legion Quiet Mode unchanged.
- Godot 4.7.2 Steam, Vulkan Forward+, 1920 × 1080, reported display 144.023 Hz.
- Populated disposable fixture `recipe_generated_4644d8cfc8f97e43`, seed 1703.
  Road origin approximately (779.38, 49.13, 1341.54). Approximately 83 m walking,
  149 m sprinting and 160 m jumping; six resident zombies in cited outliers.
- Fresh isolated derived terrain cache per run; existing engine/shader caches
  retained. Different process histories and nondeterministic worker/AI timing
  prevent treating this as a lockstep cap-only experiment.
- Production comparison: 60 FPS software cap and enabled VSync. Diagnostic:
  software cap and VSync both disabled only in that process. Saved settings,
  graphics, vegetation and power policy unchanged.

## Frame evidence

60 FPS allows **16.67 ms/frame**. Values below are elapsed frame intervals;
uncapped times are not a sum of CPU and GPU work. p99 uses the sorted sample at
`min(n-1, floor(0.99*n))`, matching the repository gate convention.

| Activity | Capped p99 / max, ms | Uncapped p99 / max, ms |
| --- | ---: | ---: |
| Idle | 18.30 / 18.79 | 12.58 / 68.10 |
| Walking | 21.70 / 25.49 | 14.14 / 18.83 |
| Sprinting | 23.10 / 45.25 | 15.95 / 22.93 |
| Jumping | 22.25 / 26.85 | 16.78 / 20.64 |
| Mining while stationary | 19.70 / 48.08 | 11.23 / 17.34 |
| Mining after running | 20.85 / 22.34 | 9.98 / 18.62 |
| Mining after jumping | 19.95 / 32.91 | 11.16 / 14.66 |
| Recovery | 18.79 / 19.99 | 15.20 / 20.09 |

Capped: 6,218 frames; 198 intervals above 20 ms, 11 above 25 ms, two above
33.33 ms. Mean movement intervals remain approximately 16.67 ms. Uncapped:
12,999 frames; mean walking/sprinting/jumping 8.60 / 8.95 / 8.62 ms, but their
tails leave substantially less headroom. The existing 20 ms p99 / 50 ms maximum
gates are already looser than strict 60 FPS; passing one is not a 60 FPS guarantee.

The 68.10 ms uncapped interval is frame index 6, early in measured idle after
profiler setup. It must be retained, but needs a longer post-setup warmup and
repeat to separate first-use/setup work from recurring steady-state stalls.

## Where the evidence points

1. **Rendering/presentation interval and uneven pacing.** Capped frame 2298
   (sprinting, position about 836.56, 50.03, 1403.38) takes 45.254 ms: 2.838 ms
   process interval, 32.067 ms draw interval, reported GPU 7.191 ms. No recorded
   draw/specialization pipeline counter changes on that frame. Engine-reported
   render CPU reaches 30.072 ms somewhere in this run. This prioritizes CPU render
   submission, synchronization, presentation and OS scheduling investigation;
   it does not identify a particular driver/engine fault or prove the limiter
   itself defective. GPU timers may lag. The uncapped early-idle outlier has
   63.184 ms draw interval but reported GPU 6.806 ms and render CPU 1.688 ms;
   the counters do not explain that wait.
2. **First-use rendering and contact work.** Capped frame 531 is the 48.083 ms
   mining outlier, with a specialization-counter increase of three, 10.457 ms
   process and 25.213 ms draw intervals. First contact dispatch costs 5.310 ms
   and contact effects 3.147 ms. This makes shader specialization and contact
   setup suspects, not proven sole causes. Mining contact-to-draw ranges up to
   49.194 ms capped and 25.309 ms uncapped. Worker queue maxima are only
   0.361 / 0.147 ms: the historical 243 ms queueing defect is not reproduced here.
3. **Main-thread streaming and publication bursts.** In the capped run, terrain
   LOD scheduling/coverage/eviction peaks at 4.916 ms; staging at 4.310 ms,
   including collision-piece attachment up to 2.903 ms. Ground-cover surface
   callbacks peak at 2.530 ms despite the shared 1 ms soft reply budget: one
   callback cannot be preempted. These are confirmed costs that consume margin,
   not explanations of every long frame. Parent/child stage timings overlap;
   do not add these maxima together.
4. **NPC simulation/admission.** Zombie update averages 0.945 ms per captured
   capped frame and peaks at 4.866 ms. One admission attachment reaches 3.625 ms;
   navigation planning peaks at 1.625 ms. Worth budgeting, but these numbers do
   not account for the 32 ms draw interval. Regular forest maintenance is small
   here: scheduler mean 4.4 microseconds, renderer mean 14.5 microseconds.
5. **Rendering has finite margin, without demonstrated memory exhaustion.**
   Capped movement GPU p99 is 8.5–9.3 ms, maximum 12.18 ms. It is not near
   16.67 ms on the cited large stalls. Sampled process-private commit peaks at
   3.57 / 3.76 GiB and dedicated GPU allocation at 1.40 / 1.41 GiB; both stay
   within repository limits. This does not rule out brief driver/resource stalls
   or qualify lower-memory machines.

## Next investigation and closure evidence

Keep the cap and visuals. Add an opt-in bounded rolling trace for ordinary play,
retaining several seconds before/after an over-budget frame and player markers.
Record frame/physics/render boundaries, subsystem work, streaming/publication
queues, shader compilation changes, position/action and presentation mode. Avoid
synchronous per-frame console/disk output, which has previously caused stalls.
The present driver writes its trace at completion and leaves parts of scene-tree
processing and engine/presentation waits unattributed; it cannot explain a drop
at an arbitrary point in a normal player session.

First repeat a foreground route with a longer measurement warmup, then use a
Windows scheduling/presentation trace on a matching captured hitch to distinguish
actual render-thread work, waits and descheduling. Targeted CPU/GPU markers can
then test contact setup, collision publication, cover callbacks and NPC admission
independently. A proposed headroom budget must be agreed explicitly; a 60 FPS
average or a relaxed gate is insufficient evidence.

Still unqualified: current player-save locations, dense furnished settlements,
combat/corpses, caves/water edits, physical driving, cold arrival, save/load during
play, long-session/thermal behavior, packaged-build parity and weaker hardware.
Return with event-correlated traces and matched before/after tail distributions;
do not close historical large stalls because they fail to recur here.
